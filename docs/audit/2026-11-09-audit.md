# akshara Audit Report — 2026-11-09

**Scope:** a P(-1) hardening, optimization and repair sweep (first-party
standards, *P(-1): Hardening*) over the whole repository outside vendored
`lib/`: `src/`, `tests/`, `dist/`, `scripts/`, the CI and release workflows,
and the documents. **Baseline:** 1.1.1 (commit `0aa7888`, cyrius 6.7.18,
rosnet 1.2.2). **Result:** 1.1.2. akshara's first standalone audit — before
this it had none of its own.

## Executive summary

No HIGH defect: nothing here is reachable through the inputs today's
consumers take from untrusted data, because attn11 validates every width and
table it hands akshara.

Two MEDIUM defects, both through the public API with invalid arguments that
the code accepted silently. **Widths:** `corpus_set` accepted any `g_data_w`,
sized the store `len * w` and then wrote 8-byte tokens for any w other than
1 or 2 — at w = 4 a 16-byte corpus wrote 64 bytes into the next heap block;
`tok_encode` did the same with its `ow`, and at `ow = 1` under a vocab past 256
it truncated ids silently (16 of 496 ids wrong, count unchanged).
**Re-learning:** a second `bpe_learn` without a fresh `corpus_set` minted ids
that collided with the merged ids already in the store — the table ended at 47
ids while the store held ids up to 66, and re-encoding the corpus no longer
reproduced it.

The rest is LOW: an unvalidated merge-table install, `corpus_set`'s refusal
path destroying the loaded corpus, out-of-range reads in `tok_emit` and
`stream_tok`, CI and test gaps (the suite was two trivial assertions and
referenced 0 of 21 library functions), and documentation drift. And speed:
`bpe_learn` 5.8–10.2× faster, `tok_encode` 5.9–6.9×, `corpus_set` 2.7×,
`gd_ld` 1.8× — every output bit-identical to 1.1.1 on x86_64 and aarch64
([ADR 0001](../adr/0001-optimizations-preserve-tokenizer-output.md)).

## Method

- **Toolchain sweeps (6.7.18):** `cyrius vet` and `cyrius deny` (clean before
  and after); `cyrius doc --check` (8 undocumented public fns in `tok.cyr`, 4 in
  `main.cyr` → 0; `cyrius audit` docs: complete); `cyrius coverage` (`tok.cyr`
  0/21 fns referenced → 21/21); `cyrius lint --strict` and `--strict-deferrals`
  on `src/` and `tests/`; `cyrius fmt --check`; `cyrius deps --verify` /
  `--locked`; `cyrius distlib --check`.
- **Manual review** of every line of `src/tok.cyr` against its callers in the
  four consumers (attn11's checkpoint loader and shard opener install tables
  and streaming state directly); a delegated read-only review of the rewritten
  file against 1.1.1. It reported no defect (6,000 random differential learns
  against 1.1.1, half with `g_paircnt` pre-filled with garbage, about 82,000
  encode comparisons, a 200,000-token streamed shard) and one over-broad guard,
  which was narrowed (finding 1: `ow = 1` was first refused for any vocab past
  256 ids, including texts 1.1.1 encoded correctly).
- **Reproductions:** every 1.1.1 defect reported below as reproduced was run
  against the 1.1.1 source (kept verbatim), not inferred from reading.
- **Golden gate:** `tests/golden.cyr` folds every output of 15 fixed corpora
  into FNV-1a digests — realistic text up to 256 KiB, single-byte runs (overlap
  and the 64-byte cap), all 256 byte values (ids to 767), binary and uniform
  alphabets, ties, every store width, the error codes. Recorded on 1.1.1 and
  asserted by the suite; the printed form (461,435 values) is `cmp`-identical
  between 1.1.1 and 1.1.2 on x86_64 and on aarch64 (qemu).
- **Oracle:** `tests/reference.cyr` keeps the 1.1.1 `bpe_learn`,
  `bpe_build_spans` and `tok_encode` verbatim; the suite compares 432 learns (6
  generators × 6 lengths × 3 widths × 4 K) and 111 encodes against it, the fuzz
  harness 1,500 random rounds.
- **Mutation testing:** 14 single-line bugs injected into the final
  `src/tok.cyr`, one at a time. The suite and the fuzz harness each killed all
  13 non-equivalent mutants — 8 in the kernels (both halves of the pair-count
  bookkeeping, the left-neighbour share rule, a stale `prevhit`, an unzeroed
  new column, the argmax tie-break, two encode off-by-ones, a dropped i64
  write-back) and 5 in the guards. Three guard mutants (the u8 boundary at id
  256, `tok_emit` at exactly `B + K`) first survived one gate and were killed
  only after boundary tests or a sharper fuzz property were added. One mutant
  (compaction starting one position early) is equivalent — it rewrites an
  unchanged prefix — and correctly survived both.
- **Benchmarks:** `scripts/bench-history.sh` (new) before and after, one
  session, median of three runs; 8 rows each, plus a single run at the 64 MiB
  loader cap.

## Findings

### MEDIUM — fixed

| # | Finding | Where | Fix |
|---|---|---|---|
| 1 | **Store and output widths were never validated.** `corpus_set` sized the store `len * g_data_w` and stored through a dispatch that writes i64 for any width but 1 and 2: w = 3…7 or > 8 overflowed the heap (reproduced: w = 4, 16 bytes → 64 bytes written into the next allocation, return value normal). `bpe_learn` kept such a width. `tok_encode`'s `ow` had the same flaw against the caller's `len * ow` buffer, and `ow = 1` truncated ids ≥ 256 without an error (reproduced: 16 of 496 ids wrong). | `corpus_set`, `bpe_learn`, `tok_encode` | `corpus_set` → **-6**, `bpe_learn` → **-5**, `tok_encode` → **-1** for a width not 1, 2 or 8. At `ow = 1`, `tok_encode` → -1 exactly when a merge minting an id past 255 applies to the text — the case 1.1.1 truncated; every text whose encoding stays below 256 ids encodes as before, whatever the vocab size. Boundary tests at ids 255 / 256; the fuzz harness checks "refused iff the i64 encoding holds an id past 255". |
| 2 | **A second `bpe_learn` corrupted the tokenizer.** Over a store that is already BPE (a second learn, or a learn after a checkpoint install), `bpe_learn` restarted from the byte base, counted pairs of ids it then could not see, and minted ids that already meant something else in the store. Reproduced: learn 40 then 20 on a 4 KiB corpus → the table claims 47 ids, the store holds ids up to 66, and `tok_encode(g_text)` ≠ `g_data` — silently, with a normal return. | `bpe_learn` | Refused with **-4** while `g_bpe_on != 0`; a fresh `corpus_set` allows learning again. The refusal changes nothing (tested). |

## Observations — not changed, and why

- **`bpe_learn` and the corpus rebuild are still one O(n) pass per merge.** At
  the 64 MiB loader cap and K = 512 they take 45.7 s and 31.5 s (1.1.2, one
  run). Removing the per-merge pass needs a position index of every pair
  (linked lists plus per-pair occurrence sets, several bytes per token —
  gigabytes at the cap), against the fixed-allocation design. A 2.x item if a
  consumer is blocked on it.
- **`bpe_learn`'s argmax is O(V²) per merge** — about 52 M cell reads over 512
  merges on the benchmark text's 27-byte base. Measured by running it twice:
  88 ms of the 129 ms 64 KiB learn (68%), 84 ms of the 820 ms 1 MiB learn
  (10%). A per-row cached
  maximum, rescanning only the rows a pass touched, would cut it; it adds a
  second invariant to the tie-break kernel for a learn that already takes
  127 ms. Not done.
- **An encoder that applies merges by rank is provably output-identical** (no
  pair of rank < m can exist when pass m starts, and a pass creates only the
  new id, so a lowest-rank-first heap reproduces the passes) and would make
  `tok_encode` O(n log n). It needs O(n) scratch per call, which the prompt
  path must not allocate. Not done.
- **`gd_ld` / `gd_st` / `decode_char` stay unchecked** — the training sampler's
  per-token reads, whose callers hold the bounds. Documented as such.
- **`corpus_set` leaves the streaming state alone.** The consumer owns
  `g_stream*` (attn11's `shard_open` sets them, and attn11 clears `g_stream`
  before every in-memory load); resetting them from `corpus_set` would leave
  the consumer's fd open behind its back. Documented.
- **`corpus_set` retains the caller's buffer** as `g_text` (no copy) — the
  checkpoint rebuild reads it later. Documented.
- **The loaders allocate 64 MiB per call** (the bump allocator never frees);
  every consumer loads once. Documented in CONTRIBUTING.
- **`stream_tok` still exits on a fatal error** rather than returning one: its
  callers are the training loop's samplers, which have no error path, and a
  stale token must not reach the weights.
- **The fuzz harness runs on x86_64 only in CI** (~10 s; about 80 s under
  qemu). The suite, with the golden digests and the oracle matrix, runs on
  both.
- **action-gh-release v3.0.4** was released after rosnet and tyche pinned
  v3.0.3; v3.0.3 is kept for parity across the three repositories.
- **`lib/agnosys.cyr`** was removed in 1.1.1 (maintainer-approved), so `lib/`
  is exactly the 6.7.18 snapshot plus rosnet and tyche.

## Downstream

No public signature changed, and every output on a valid input is
bit-identical to 1.1.1 (golden digests and the full dump, both targets). New
error returns appear only for arguments that were undefined behaviour or a
silently wrong result before: `corpus_set` -6, `bpe_learn` -4 / -5,
`bpe_build_spans` -1, `tok_encode` -1, `tok_emit` -1, `corpus_load_file` -2 for
an over-reporting hook. One consumer note: attn11's checkpoint rebuild
(`persist.cyr:506`) assigns `tok_encode`'s result to `g_datalen` without a
check. It passes `g_data_w`, which is 2 under BPE, so no new return reaches it
today; a u8 BPE rebuild would now get -1 where 1.1.1 gave truncated ids. The bundle
needs one hook fewer (`puts`) and its sidecar is unchanged (`io`). The four
consumers' call patterns were read (attn11's `persist.cyr`, `stream.cyr`,
`train.cyr`, `main.cyr` and tests; tarka, tentib and prajna call only
`corpus_set` and the accessors): every call is valid under 1.1.2. Consumers'
suites were not re-run.
